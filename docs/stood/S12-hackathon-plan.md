# S12: Hackathon plan

The lead demo is Adaeze buying a code milestone; [S09](S09-demo-script.md) is the six-beat target. Deadline and sponsor rules remain recorded in the historical [brief](../06-paypal-hackathon.md); recheck them before submission.

## Evidence-led delivery

| Round | Goal | Exit evidence |
|---|---|---|
| Current | Code profile and full doc alignment | Synthetic profile tests; source-linked docs; no runner claim |
| Funding / recovery | Durable approval/authorisation, missed-send retry and renewal queue | Fake-provider and real-Postgres races first, then actual sandbox qualification |
| Code evidence | Frozen tests, read-only fetch, isolated runner and trusted report ingestion | Isolation/attack fixtures, signed exact-commit reports and mutation evaluation |
| Usage / agents | Outside receipt, human acceptance, bounded Yard task and A2A/AP2 contracts | Independent authority/replay tests and separately qualified protocol/operator integration |
| Product / submission | Reviewer, Gantt, receipts, notifications and video | Usable screens, provider IDs, accessible copy, reproducible judge path |

Impact is code delivery with accountable agent operators, not a self-funding agent chain. Models explain findings without payment tools. Presentation distinguishes the storyboard, synthetic rule evidence and actual provider execution. EyeOnSite remains a scenario.

## Sponsor strategy

Each partner has one justified job and an honest planned/implemented label; [S13](S13-sponsor-integration.md) re-evaluates fit. Channel3 is weaker for code milestones and stays optional in the field scenario. Do not spend qualification time on a decorative integration. At least five tasks per review round, one signed commit per task, tests first for money behaviour.
